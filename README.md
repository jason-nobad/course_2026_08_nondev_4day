## 2. 이 저장소를 내 것으로 만들기 (Fork)

첫날 실습 1에서 강사 시연 후 함께 진행합니다. 미리 해 두어도 좋습니다 — 전부 웹 화면 클릭입니다.

1. 이 페이지 오른쪽 위의 **Fork** 버튼을 누릅니다.
2. Owner(소유자)에 내 계정이 선택된 것을 확인하고 **Create fork**를 누릅니다. → `github.com/내계정/저장소이름` 이 생깁니다. 이제부터 이곳이 **우리 페어의 팀 저장소**입니다.
3. 페어당 저장소 1개를 씁니다. 한 사람이 Fork 했다면 **Settings → Collaborators → Add people**로 짝을 초대하세요.
4. 앞으로 만드는 모든 결과물은 이 저장소에 **커밋(저장)** 합니다. 커밋 이력이 곧 4일간의 작업 기록이자 감사(audit) 자료가 됩니다.

> **왜 저장소인가?** 도구(AI 서비스)는 계속 바뀌지만, 잘 쓰인 업무 매뉴얼(스킬)·흐름도·체크리스트는 어느 AI에게든 통하는 **팀 자산**으로 남습니다. 이 저장소는 교육 소품이 아니라 **부서 스킬 저장소 1호**입니다.

## 5. 결과물 두는 곳 (권장 폴더 구조)

결과물을 넣을 폴더가 **미리 만들어져 있습니다.** 각 폴더 안의 `README.md`에 무엇을 언제 넣는지, 문서 틀은 어떻게 생겼는지 적혀 있으니 먼저 열어 보세요. 폴더 이름은 팀 규칙으로 바꿔도 되지만, **정하고 나면 4일 내내 지키는 것**이 중요합니다 — 산출물 위치 혼선이 가장 흔한 실패 원인입니다.

```
(내 저장소 루트)
├── README.md            ← 4일차에 "우리 팀 파일럿 패키지" 목차로 완성 (아래 6절)
├── index.html           ← 샘플 패키지 표지(4일차 완성 모습). 2일차에 본인 안내 홈페이지로 교체 → 4일차에 패키지 표지로 확장
├── .nojekyll            ← Pages가 파일을 그대로 배포하게 하는 빈 파일 — 지우지 마세요
├── materials/           ← 강의 자료 PDF (참가자 안내서·카탈로그·사전학습·슬라이드) — 읽기용
├── docs/                ← 슬라이드 웹 버전(day1~4.html, 발표 모드) — 읽기용
├── References/          ← 스킬·디자인 예시와 근거 문서 — 읽기용
├── Skills/              ← 스킬 v0 메모(1일) → 스킬 v1.0(2일, PR 병합) · 용어집 · 금지 행동
├── Workflow/            ← 업무 흐름도(Mermaid, 2일 과제) · RACI · 예외 경로(3일)
├── Outputs/             ← 업무 문서(1일) · 우선순위 표 · 검증 체크리스트(3일 과제) · KPI 표 · 브리프(4일)
├── Tool/                ← 3일차 업무용 프로그램 · 사용법 · 샘플 3종 검증 기록
└── _workspace/          ← 폴더 규칙 — 원본 / 작업 중 / 최종 구분 (3일차에 팀 규칙 완성 · 비식별 샘플만!)
    ├── 01_input/        원본(입력) — 손대지 않음
    ├── 02_working/      작업 중
    └── 03_final/        최종 산출물
```

### 샘플로 먼저 보기 — 가상 사례 "㈜가온물산 구매팀 · 주간 업무 보고 자동화"

각 폴더의 `sample_*` 파일과 루트의 `index.html`은 **하나의 가상 사례**를 4일 순서대로 끝까지 만들어 본 것입니다 (실습 주제 카탈로그 01번). 우선순위 표 → 업무 문서 → 스킬 v1.0 → 흐름도 → 도구 → 샘플 3종 검증 → 체크리스트 → KPI → 브리프 → 패키지 표지(index.html)까지 서로 이어져 있으니, 막힐 때 "이 단계의 결과물은 이렇게 생겼구나"로 참고하세요. 회사·인물·수치는 모두 가상입니다.

도구는 실제로 돌아갑니다 — 저장소 루트에서:

```bash
python3 Tool/sample_weekly_report_tool.py sample_normal --date 2026-08-14
```

`_workspace/01_input/sample_normal/`의 메모 3건을 읽어 `_workspace/02_working/`에 초안을 만듭니다. `sample_edge`(경계)·`sample_error`(오류)로 바꿔 돌리면 3일차 "샘플 3종 검증"을 그대로 체험할 수 있습니다. 본인 실습을 시작하면 `sample_` 파일은 지워도 됩니다.

### GitHub Pages로 배포하기 (4일차)

1. 저장소 **Settings → Pages**
2. **Source**를 "Deploy from a branch", Branch를 `main` / `/ (root)`로 선택 → **Save**
3. 1~2분 뒤 `https://내계정.github.io/저장소이름/` 에서 `index.html`이 열립니다.
4. 이후 커밋할 때마다 자동으로 다시 배포됩니다 — "레포가 원본이고, 배포는 따라온다."

> **미리 체험:** 이 저장소에는 샘플 패키지 표지 `index.html`이 이미 들어 있어, Fork 직후 위 순서만 따라 하면 **가상 사례(가온물산 구매팀) 패키지 페이지가 바로 웹 주소를 갖습니다.** 페이지의 "열기" 링크는 자동으로 내 저장소의 파일을 가리킵니다. 4일차에는 이 페이지를 본인 패키지 내용으로 바꾸면 됩니다.
> `.nojekyll`(빈 파일)은 Pages가 `_workspace/` 같은 밑줄 폴더와 `.md` 파일을 가공하지 않고 그대로 두게 하는 설정입니다 — 지우지 마세요.

## 7. 꼭 지켜주세요 — 모든 실습에 공통

교육 첫날부터 실무까지 동일하게 적용되는 원칙입니다. (상세: `materials/02_practice_topics.pdf` 4장 "Best Practice 8가지")

1. **비식별 원칙** — 고객 실명, 실제 계약 금액, 사내 기밀이 담긴 실데이터는 교육장과 이 저장소에 **절대 올리지 않습니다.** 반드시 가명·더미 값으로 바꾼 비식별 샘플만 사용합니다. (이 저장소는 GitHub Pages로 **공개**됩니다.)
2. **사람 검토 없는 자동 발송 금지** — 외부로 나가는 산출물은 반드시 사람의 승인을 거칩니다. 흐름도에 승인자를 이름 또는 역할로 명시합니다.
3. **스킬은 업무 매뉴얼처럼** — 목적·절차·금지 사항·예시 입출력이 없는 스킬은 미완성입니다. 좋은 예시 1건 + 나쁜 예시 1건이 규칙 10줄보다 효과적입니다.
4. **폴더 규칙(`_workspace`) 먼저** — 입력·작업 중·최종을 분리하고 이름 규칙을 정한 뒤 시작합니다.
5. **검증 체크리스트를 산출물보다 먼저** — "무엇이 통과인가"를 먼저 정의합니다.
6. **모르면 멈추고 질문** — 입력이 불충분하면 임의로 채우지 말고 "확인 필요"로 표시하도록 스킬 금지 사항에 넣습니다.
7. **근거 인용 강제** — 요약·답변류는 원문 인용 또는 출처 링크 필수, 근거 없는 항목은 삭제합니다.
8. **버전과 변경 기록** — 스킬은 v1, v1.1처럼 버전을 붙이고 변경 사유를 한 줄씩 남깁니다.
