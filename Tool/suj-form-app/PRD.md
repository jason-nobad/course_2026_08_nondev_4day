# PRD — 정책 애로사항 접수 시스템(suj-form-app) 향후 개선 방향

> 현재 배포된 v1.2(3-tier: Vercel/Render/Supabase, 공개 접수 폼 + 내부 조회·상태변경·CSV 다운로드 화면)를 기준으로,
> 다음 단계에서 무엇을 어떤 순서로 개선할지 정리한 문서입니다. 실제 운영 중 발견된 제약을 근거로 작성했습니다.

## 1. 배경

`docs/suj_form.html`(정적 mailto 양식)을 3-tier(Vercel·Render·Supabase)로 재구성하고, 이어서 내부용 조회 화면(`admin.html`)에 상태 변경과 엑셀 다운로드를 붙인 상태입니다. 접수 자체는 실사용 가능한 수준이지만, "접수 → 담당자 배정 → 처리 → 종결"까지의 업무 흐름과 여러 담당자가 함께 쓰는 것을 전제로 한 기능은 아직 없습니다. 이 문서는 그 다음 단계를 위한 것입니다.

## 2. 현재 시스템 요약

| 계층 | 내용 |
|---|---|
| Presentation | `frontend/index.html`(공개 접수 폼 + 접수번호 조회), `frontend/admin.html`(내부 목록·상태변경·CSV 다운로드) |
| Application | `backend/server.js` — Express, `/api/complaints`(등록), `/api/complaints/:receiptNo`(본인 조회), `/api/admin/complaints`(목록), `/api/admin/complaints/:receiptNo/status`(상태변경) |
| Data | Supabase `complaints`/`complaint_seq` 테이블, RLS로 잠겨 있고 백엔드 `service_role` 키만 접근 |
| 인증 | 공개 폼은 인증 없음(의도된 설계). 관리 화면은 공유 키(`ADMIN_KEY`) 하나로 여는 최소 보호 |

## 3. 지금까지 확인된 제약 (개선 과제의 근거)

1. **첨부파일이 아예 없음** — 접수 폼에 파일 입력 자체가 없고 Supabase Storage 연동도 없음. "증빙 자료는 담당자에게 별도 전달"이 유일한 경로.
2. **관리자 인증이 공유 키 하나** — 로그인/역할 구분이 없어 누가 무엇을 바꿨는지 알 수 없고, 키가 유출되면 전원 접근 가능.
3. **상태 변경 이력이 안 남음** — `complaints.status`를 덮어쓰기만 해서 "언제·누가·왜 바꿨는지"가 사라짐.
4. **`Tool/complaint_management_system.html`과 완전히 분리** — 회원사·처리이력·기관협의·정책건의를 다루는 본격 관리자 도구가 있지만 localStorage 기반이라 이 Supabase DB와 무관하게 동작. 실제 접수 건이 그 도구의 업무 흐름(담당자 배정·기한·종결사유 등)으로 들어가지 못함.
5. **알림이 없음** — 신규 접수·긴급 건이 와도 담당자에게 알려주는 수단이 없어 `admin.html`을 수시로 열어봐야 함.
6. **Render 무료 인스턴스가 15분 유휴 후 슬립** — 첫 요청이 최대 50초 지연될 수 있음. 접수자 경험에 직접 영향.
7. **Render가 GitHub App이 아닌 "Public Git Repository" 방식으로 연결됨** — push해도 자동 배포되지 않고 매번 대시보드에서 수동으로 "Deploy latest commit"을 눌러야 함. (Vercel은 GitHub App 연결이라 자동 배포됨 — 비대칭)
8. **속도 제한이 공개 API와 관리자 API에 동일하게 적용** — `/api/` 전체에 15분당 30회. 관리자가 여러 건을 빠르게 처리하면 스팸 방지용 제한에 걸릴 수 있음.
9. **접수번호 채번 규칙이 두 시스템에서 다름** — `suj-form-app`은 연도별로 리셋(`EDPA-2026-0001`), `complaint_management_system.html`은 리셋 없이 계속 증가. 두 시스템을 나중에 연동하면 번호 체계부터 충돌.
10. **CSV 다운로드가 화면에 로드된 것만 대상** — 현재 목록 API가 최대 200건만 반환(`limit(200)`)하므로, 접수량이 늘면 다운로드에서 누락되는 건이 생길 수 있음.

## 4. 개선 과제 — 우선순위

| 우선순위 | 과제 | 이유 |
|---|---|---|
| P0 | 상태 변경 이력 로그 | 지금 당장 데이터 유실 위험(누가 언제 왜 바꿨는지 못 씀). 스키마 변경만으로 가능, 작음 |
| P0 | Render 자동 배포 전환 | 코드는 이미 있는데 매번 수동 배포를 잊으면 실제 서비스가 낡은 버전으로 남음. 설정만 바꾸면 됨 |
| P0 | CSV 다운로드 전체 건수 대응 | 지금도 200건 넘으면 조용히 누락됨 — 데이터 정합성 문제 |
| P1 | 관리자 인증을 Supabase Auth로 전환 | 여러 담당자가 쓰기 시작하면 공유 키로는 책임 소재 추적 불가 |
| P1 | 신규/긴급 접수 알림 (이메일 또는 Slack) | 담당자가 능동적으로 화면을 열어야만 아는 구조는 놓치기 쉬움 |
| P1 | 첨부파일 업로드(Supabase Storage) | 지금은 "별도 전달"이라 접수-증빙이 한곳에 안 모임. 사용자 요청 있었으나 이번 범위에서 보류함 |
| P2 | `complaint_management_system.html`과 데이터 연동 | 가치는 크지만 스키마가 근본적으로 다르고(11단계 상태 vs 7단계, 담당자·부서·기한 등 워크플로 필드 전체 부재) 재작업 범위가 큼 — 별도 프로젝트로 진행 권장 |
| P2 | Render 유료 플랜 전환 (슬립 방지) | 비용이 드는 결정이라 사람이 판단 |
| P3 | 관리자 화면 검색·필터(상태별/기간별/긴급만 보기) | 접수량이 늘어난 뒤에 필요해짐 |
| P3 | 접수번호 채번 규칙 통일 | 두 시스템 연동(P2) 착수 시점에 같이 결정 |

## 5. 과제 상세

### 5.1 상태 변경 이력 로그 (P0)

- **문제**: `UPDATE complaints SET status = ...`로 이전 상태·변경자·시각·사유가 사라짐.
- **제안**: `complaint_status_log` 테이블 추가(`id, receipt_no, from_status, to_status, changed_at, note`). `create_complaint`처럼 Postgres 함수(`update_complaint_status`)로 상태 변경 + 로그 기록을 한 트랜잭션에 묶는다. 백엔드 `PATCH .../status`가 이 함수를 호출하도록 변경.
- **완료 조건**: `admin.html`에서 각 건의 "이력 보기"를 눌러 변경 내역(이전 상태 → 이후 상태, 시각)을 볼 수 있다.
- **비고**: `note`(변경 사유)를 관리자 화면에서 선택 입력받으면 나중에 감사 목적으로도 쓸 수 있음.

### 5.2 Render 자동 배포 전환 (P0)

- **문제**: `Tool/suj-form-app/backend/render.yaml`이 이미 있지만, 현재 서비스는 "Public Git Repository" 방식으로 만들어져 push해도 자동 배포되지 않음.
- **제안**: Render 대시보드에서 GitHub App을 설치하고 기존 서비스를 재연결(또는 서비스를 새로 만들어 `render.yaml` 기준 Blueprint로 전환). 이후 `main` push 시 자동 배포되는지 확인.
- **완료 조건**: 코드를 push하면 별도 수동 조작 없이 몇 분 내 새 버전이 `Live`가 된다.

### 5.3 CSV 다운로드 전체 건수 대응 (P0)

- **문제**: `GET /api/admin/complaints`가 `limit(200)`이라 200건을 넘으면 오래된 건이 다운로드에서 조용히 빠짐.
- **제안**: 우선 페이지네이션(`?page=`) 또는 전체 조회 전용 엔드포인트(`/api/admin/complaints/export`, limit 없음 또는 훨씬 큰 값)를 추가. `admin.html`의 다운로드 버튼은 화면에 이미 로드된 목록이 아니라 이 export 엔드포인트를 호출하도록 변경.
- **완료 조건**: 접수 건이 200건을 넘겨도 CSV에 전 건이 포함된다.

### 5.4 관리자 인증을 Supabase Auth로 전환 (P1)

- **문제**: `ADMIN_KEY` 공유 키 하나 — 누가 접속했는지, 누가 상태를 바꿨는지 구분 불가.
- **제안**: Supabase Auth(이메일/비밀번호 또는 매직링크)로 담당자별 로그인 도입. `profiles` 테이블(사용자 ↔ 이름/역할)을 추가하고, 상태 변경 이력(5.1)의 `changed_by`를 실제 사용자로 채운다. `ADMIN_KEY` 방식은 이 전환 전까지 유지.
- **완료 조건**: 담당자가 각자 계정으로 로그인하고, 상태 변경 이력에 실제 담당자 이름이 남는다.

### 5.5 신규/긴급 접수 알림 (P1)

- **문제**: 접수가 들어와도 담당자가 능동적으로 `admin.html`을 열어야만 알 수 있음.
- **제안**: Supabase의 `create_complaint` 함수 성공 시 백엔드에서 Slack Webhook 또는 이메일(Resend 등)로 알림 발송. 긴급(`urgent = '긴급'`) 건은 별도로 강조.
- **완료 조건**: 접수 즉시 지정된 채널에 회사명·요약·접수번호가 포함된 알림이 온다.

### 5.6 첨부파일 업로드/다운로드 (P1, 이번 라운드에서 보류됨)

- **문제**: 공개 폼에 파일 입력이 없고 Supabase Storage 연동도 없어 다운로드할 대상 자체가 없음.
- **제안**: (a) `complaints` 관련 Storage 버킷 생성 + RLS 정책, (b) 공개 폼에 `<input type="file">` 추가 후 접수 시 업로드, (c) `admin.html`에 파일 목록·다운로드 링크 추가. 업로드 용량·파일 형식 제한 필요(스팸/악성 파일 방지).
- **완료 조건**: 접수자가 증빙 파일을 첨부해 제출하면, 관리 화면에서 해당 파일을 내려받을 수 있다.

### 5.7 `complaint_management_system.html`과 데이터 연동 (P2)

- **문제**: 두 시스템의 "민원" 개념이 근본적으로 다름(상태 11종 vs 7종, 담당자·부서·기한·기관협의 등 워크플로 필드가 관리 도구 쪽에만 있음). 단순 병합이 아니라 스키마 재설계가 필요한 작업.
- **제안**: 별도 설계 단계로 분리해서 진행. (1) 공개 접수가 관리 도구의 "신규접수" 큐에 그대로 들어가도록 `complaints` 스키마를 확장(담당자·부서·기한·상태11종 등 추가), (2) `complaint_management_system.html`의 `Backend.*` 함수들을 localStorage 대신 Supabase 호출로 전환(전부 비동기화 필요), (3) 로그인은 5.4의 Supabase Auth를 그대로 사용.
- **비고**: 이전 세션에서 이 파일의 데이터 모델·API 전수 분석을 이미 해뒀음 — 착수 시 그 결과를 그대로 설계 입력으로 쓸 수 있음.

### 5.8 Render 유료 플랜 전환 (P2)

- **문제**: 무료 인스턴스는 15분 유휴 후 슬립, 첫 요청이 최대 50초 지연.
- **제안**: 실사용 트래픽이 생기기 시작하면 Render 유료 플랜(Starter 이상)으로 전환 검토. 비용이 드는 의사결정이라 담당자 판단 필요.

### 5.9 관리자 화면 검색·필터 (P3)

- **제안**: `admin.html`에 상태별·긴급여부별·기간별 필터, 회사명/접수번호 검색 추가. 접수량이 늘어난 뒤 우선순위 올리기.

### 5.10 접수번호 채번 규칙 통일 (P3)

- **제안**: 5.7 착수 시점에 두 체계(연도별 리셋 vs 무한 증가) 중 하나로 통일할지, 접두사를 다르게 유지할지 결정.

## 6. Out of scope (이번 문서에서 다루지 않음)

- 모바일 전용 UI/반응형 고도화 (현재도 기본적인 반응형은 되어 있음, 별도 요청 시 진행)
- 다국어 지원 (현재 한국어 전용, 회원사 대상 서비스 특성상 우선순위 낮음)
- 결제/과금 관련 기능 (해당 없음)
